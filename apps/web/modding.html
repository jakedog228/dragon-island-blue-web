Modding guide

Start with an asset archive for game data and resources. Add an Offline JavaScript mod to change behavior, renderers, or interface code. This guide covers both workflows, from a first mod to the importer's validation gates and the runtime's required asset roles.

What a package is

An asset archive is a ZIP-compatible file (.ipa or .zip) with one resource root containing property lists, PNGs, bitmap fonts, audio, and a Localizable.strings dictionary. The importer classifies it by structure only; the file name, app name, bundle identifier, and any executable inside are never inspected or trusted.

Loading happens entirely in the browser tab. The loader reads the bytes with the File API, discards executables and signing data, parses resources in memory, and exposes them through session-scoped blob: URLs. Nothing is uploaded. After a successful import and your rights attestation, the exact compressed archive may be cached in this browser so a reload can restore it; a different byte stream needs a new attestation.

Import checks stop at the first failure and report it in the loader's status line. Other schema, reference, or mechanic errors can appear at play start or when a feature runs. The loader message index identifies the stage; passing import alone does not validate every reachable feature.

First JavaScript mod

Create this directory, with the manifest at its root:

my-mod/
├── manifest.json
└── scripts/
    └── main.js

manifest.json:

{
  "schemaVersion": 4,
  "id": "dev.example.inspector",
  "version": "1.0.0",
  "displayName": "Runtime Inspector",
  "apiVersion": 4,
  "mode": "offline",
  "dependencies": {},
  "entry": "scripts/main.js"
}

scripts/main.js adds a diagnostic field to the battle's text projection. The entry is an async function body receiving dibMod: top-level await works; static import declarations do not. Compile or bundle TypeScript to the declared JavaScript file before packaging. 

const { BattleNode } = await dibMod.modules.load("web/battle/battleNode.ts");

dibMod.intercept(BattleNode.prototype, "renderGameState", function (next, ...args) {
  return { ...next(...args), myInspector: { active: true } };
});

dibMod.hooks.on("boot:ready", ({ value }) => {
  console.info("Inspector ready", value.scenes);
});

From the directory containing my-mod, package its contents using Python:

python -m zipfile -c inspector.zip my-mod/manifest.json my-mod/scripts
python -c "from pathlib import Path; Path('inspector.zip').rename('inspector.dibmod')"

Select a compatible base archive in the loader, open the Mod Manager under it, choose Import file (or drop inspector.dibmod onto it), apply, and launch Offline. Enter a battle and inspect window.render_game_to_text() in the browser console: the battle projection includes myInspector.active. A mod ZIP is an overlay, not a replacement for the base game's resource archive.

Manifest and load order

All eight fields in the quick-start manifest are required. Unknown manifest keys are rejected. IDs use lowercase reverse-DNS form; versions use major.minor.patch with an optional prerelease suffix. The entry must be UTF-8 .js or .mjs. The relation fields below default to empty except the required dependencies map; priority defaults to 0:

FieldMeaning
dependenciesRequired ID-to-version-range map; a missing dependency or incompatible version refuses the profile.
optionalDependenciesVersion-check and order a dependency only when it is selected.
conflictsRefuse matching selected packages unless the player chooses Load anyway.
loadAfter, loadBeforeArrays of IDs establishing order when those packages are present.
priorityInteger from −1,000,000 to 1,000,000, default 0. Higher loads later among otherwise unordered packages; ID breaks ties.

Ranges support *, exact versions, comparison operators, ^, ~, space-separated conjunctions, and || alternatives. Selection order is ignored. Dependency and ordering edges precede priority; a manual drag in the Mod Manager's Load order tab cannot bypass an edge or resolve a cycle; that tab marks each mod's recommended position (its own priority and edges, ignoring manual moves). Later replacements win, while interceptors can compose by calling next.

Mod archive limits differ from base archives: 64 MiB compressed, 128 MiB expanded, 512 entries, 32 MiB per entry, and a maximum 250:1 per-entry compression ratio. Duplicate or unsafe paths, unsupported compression, invalid manifests, and dependency cycles are rejected. These are integrity checks, not restrictions on executed mod code.

Lifecycle and cleanup

Register dibMod.hooks.on(name, ({ value, host }) => …) during entry execution. Handlers run in resolved mod order. A non-undefined return replaces the phase value for subsequent handlers, so observation-only handlers should return nothing.

Phase, in orderAvailable value
mods:readyInterference report after every package entry has executed; a place for compatibility patches.
content:loadedImported content before save fingerprinting. Return a replacement package to overlay data; retain the resource catalog, manifest, and disposal contract.
boot:startingDOM host, acquired content/save connection, scene coordinator, and startup diagnostics.
boot:readyDOM/render hosts, content, scenes, Pixi stage, keyboard, audio, diagnostics, and deterministic advanceTime.
game:loadedLoadedGame; may return a replacement.
startup:loadedStartup result/save session, game, stage, scenes, audio, and content.

Completed phases are also stored under their names in dibMod.host; content and game are published directly. Return new data objects when editing phase values so the interference report can attribute changed leaves. In-place mutations can evade that comparison. Reports describe overlap; they do not prove compatibility.

Disposal restores properties patched with replace/intercept and revokes URLs created with files.url. Direct assignments and arbitrary browser side effects cannot be automatically undone. Own your cleanup, including renderer restarts and scene transitions; a full page reload establishes a clean realm.

Profiles and saves

The gate caches recently used mod archives and remembers save-linked profiles on this device. Use restores a profile when its mod bytes remain cached. Disable all in the Mod Manager, then Apply, clears the selection and suppresses automatic profile restoration; if code already ran, applying reloads the page so Online can become available again.

Save namespaces use effective mechanics-bearing content data after the content:loaded overlay. Exact mod bytes and resolved order identify the profile, but do not themselves select the save namespace. Code-only and visual updates can therefore share saves; profile changes still display a warning because code changes can alter save semantics without changing the data fingerprint.

Try here clones a foreign profile's slot into a free current slot, retaining the original. This is an explicit compatibility override and can produce a broken clone. Delete confirms removal of one slot and its rollback revisions; it leaves other slots, cached packages, and profile metadata intact. Export a backup before testing incompatible data or save behavior.

Examples and debugging

Build the repository's selectable examples:

pnpm mods:examples

Output is examples/mods/dist/*.dibmod. Start with blue-dragon-overdrive for a content overlay, devtools for runtime/UI interception, fire-cub-inferno-barrage for a move composed with another mod, or mercy-stone for an item spanning data, assets, shop, and battle. Their sources live under examples/mods/.

Check the resolved order and shared seams in the Mod Manager's Load order tab, browser console errors, and window.render_game_to_text(). For deterministic scenarios, use short window.advanceTime(ms) bursts. Test the mod alone and with its declared dependencies, then exercise scene changes, reload, save/restore, and Disable all. Browser validation is opt-in and must launch Chromium with --mute-audio.

The full TypeScript API and compatibility guidance are available as code-mod-api.md. The archive contract below applies to the base resource importer; executable mods have the separate full-trust boundary described above.

3World scan

If Worlds.plist exists, its keys become the package's world names and one <world>.plist is expected per key. A package has town capability when any world's pointsOfInterest[].arguments contains a buildings key. Town-capable packages must also provide a strict Towns.plist registry (see Town); a bad registry fails with Invalid Town Portal registry: …. Without Worlds.plist the package is battle-only and this gate is skipped.

4Quest catalog

A present Quests.plist is never treated as opaque. It must be an ordered array of records with unique nonempty name values and one of the twelve implemented quest classes, each with its exact field vocabulary. Duplicate names, unknown classes or keys, nonpositive quantities or floors, reversed floor ranges, and malformed battle-key arrays fail with Invalid Guild quest catalog: …. challengeLevel is clamped to a minimum of 1.

5Dungeon scan

The presence of Dungeons.plist, Rooms.plist, or any Dungeon_*.plist marks the package as dungeon-capable. Once marked, a partial set is rejected rather than silently disabling dungeons: Incomplete dungeon resources: <missing list>. The required set is listed under Dungeon. Packages with no marker skip this gate.

7Reward paths

Only when Quests.plist is present: the importer resolves the full strict data set (this is the first point where schema errors can surface) and parses every quest's treasureData. Each fixed items[].data.type is a dotted Items.plist key path, not a reward name from a fixed list. The resolved leaf's class decides behavior: Item becomes a durable inventory item, Egg with a positive integer arguments.numRepeats becomes the Clone Egg route, and anything else fails with Invalid Guild quest reward catalog: ….

8Collection route

Every world is scanned for a POI whose menu class is MonsterCollectionMenuItem. A promoted route requires Collection.plist with the exact authored collection-type root plus the presentation roles listed under Collection. A package with no promoted route may omit the catalog entirely; a present catalog is still parsed strictly (Invalid Collection resources: …).

11Render manifest

The importer projects retained files into the renderer manifest. This is where atlases, fonts, particles, audio, and world or dungeon presentation roles are checked.

  1. If Worlds.plist exists, every data-referenced world and POI sprite is collected and the world presentation roles (plus town roles when town-capable) are validated. Failures read Invalid world resources: …, World resources require …, or Town resources require ….
  2. If dungeon-capable, Sparkle.plist must resolve its texture and every theme's room-atlas frames, pickup frames, and spirit-totem portraits are checked.
  3. If Menus.plist exists, every *.fullScreenBackground PNG it names must be a root-level file and is projected.
  4. Every *-hd.plist that parses as a Cocos format-2 atlas becomes a Pixi sheet. Its texture resolves through the derived <stem>.png first, then the plist metadata (Atlas … references missing texture …).
  5. Standalone PNGs enter the sprite manifest when the stem ends in -hd, -ipadhd, or Combat, or the file is data-referenced, or it is one of the fixed bare roles listed under Standalone sprites.
  6. Every *-hd.fnt must declare a page file; the importer prefers <page>-hd.png and falls back to the named page (Bitmap font … has no page texture. / … references missing texture …).
  7. Every particle plist with a textureFileName must resolve it (Particle … references missing texture …).
  8. Audio files are keyed by extensionless stem. Files are visited as .m4a, then .mp3, then .wav, and a later format with the same stem replaces the earlier entry. Avoid same-stem collisions unless that precedence is intended.

12Combat background

At least one bare <Biome>Combat.png (stem ending in Combat, not -hd) at 1024×768 or larger must be present. Bare combat images are cropped by source-derived renderer rules; an overworld texture is not a substitute. Otherwise: No bare <Biome>Combat.png battle background was found.

After import: play start

Passing the importer makes the archive selectable and enables the play modes. When a slot starts, the engine resolves inheritance and validates every monster, job, ability, and component against the strict schemas in packages/gamedata/src/schemas.ts, loads each world through the typed world loader, and preloads the manifest. A schema failure at this stage appears in the same status line as a loader message; the README calls this case "the archive parses but cannot start".

Some data errors surface even later. Ability construction arguments may come from the ability dictionary, the component reference, or the job-ability reference, and a missing argument only fails when that move is selected in battle. The opt-in archive test in Validate runs authored moves to a terminal state to catch those.

Data contract

Schemas are strict: an unknown key is an error, not metadata. Keep display names and descriptions in Localizable.strings, never as extra fields on data nodes.

Inheritance

Dictionaries are trees of dotted paths (Fire.Emberling). A node is a definition when it has parent, class, index, or jobAbilities, or is named as some other node's parent; grouping containers are not resolvable on their own. Child keys deep-merge over the resolved parent, with one exception: a child-authored jobAbilities.<slot> replaces that slot wholesale, so repeat every argument the replacement needs.

A child job that declares parent may omit jobAbilities (or author an empty one) and keeps every parent slot. This does not fabricate a job for a monster that has no matching Jobs.plist entry.

Monsters

A resolved monster leaf must contain exactly these keys.

Items and soul stones

Items.plist is the strict definition catalog for soul stones, usable items, Gems, and Eggs. When soul-stone behavior is reachable it must contain all seven SoulStones.<Element>SoulStone leaves: 

class: SoulStone
slot: Monster
stats: { Attack: true, … }   # partial map of stat name to boolean

A usable quest reward points at any dotted path whose leaf has class = Item, slot = Useable, and a rendererData.spriteFrame present in InventoryItemFrames-hd. Optional creation arguments.level defaults to 1; a definition-level level takes precedence. Items can be received, inspected, grouped, and dropped; there is no generic Use command. Runtime item state belongs to the save, never to catalog leaves.

The Clone Egg is an Items.plist leaf with class = Egg (normally DestroyOnPickup.RepeatEgg) referenced by a fixed reward with positive integer arguments.numRepeats. It additionally needs RenderableRepeatEggNameKey, RepeatEggTitleKey, RepeatEggMessageKey, and RepeatEggSelectionTitleKey. Clone Egg and generic-Item rewards are local-only: Online packages that make them reachable fail with CAPABILITY_UNSUPPORTED.

A Store building needs the root sprites ShopScreen.png and buy.png; opening the Store fails loudly if either is missing. Stock and prices come from the catalog; payment uses profile silver or gold; external purchase is absent and fails closed.

Licenses

When Character/Gem or Arena progression is reachable, Licenses.plist must contain exactly Novice, Apprentice, Veteran, Expert, Elite, Master, and Grandmaster, each with hero/quest requirements, challenge level, batting-order size, Gem slot count, and monster populator. Slot and challenge progression are ordinal, so a missing intermediate license fails loading instead of shortening the chain.

Combines

Combines.plist is a flat dictionary from a Combine-category result type to exactly two ordered ingredient types, all resolvable through Monsters.plist. Order is gameplay-significant: the Monsterpedia picker fills the two slots in authored order, and a repeated-species recipe needs two distinct monster instances. This file is the only recipe relation; no metadata flag can unlock a recipe or enable combining outside a town.

Localization

Use a plist-compatible .strings dictionary with string values. Every renderable, move, popup, status, quest, chat, world, and town key referenced by data must resolve. Structural UI keys checked by the startup, Egg, town, and Collection gates are runtime API: keep them synchronized with validate_current_runtime() in the reference builder.

Assets

Expressive art and audio are yours. Structural names are the renderer's. Every data reference and every required role must resolve within the resource root.

Atlases

Cocos format-2 atlas plists whose stem ends in -hd are converted to Pixi sheets. Keep geometry source-shaped and do not swap rotated frame dimensions; Pixi handles rotation. The texture resolves through <stem>.png first, then the plist's metadata filename. All named frames referenced by data must belong to an included owning atlas; a PNG consumed as an atlas sheet is not also exposed as a standalone sprite.

Standalone sprites

A PNG enters the sprite manifest when any of these hold:

  • its stem ends in -hd, -ipadhd, or Combat;
  • it is referenced by world, POI, town building, dungeon, or Menus.plist data;
  • it is one of the fixed bare roles: mainscreenBackground.png, saveSlotBackground.png, monsterEvolved.png, MMScreen.png, ShopScreen.png, buy.png, bigmap.png, bookPage.png, leaveIcon.png, Icon.png, Icon@2x.png, lock@2x.png, or a recognized Plot frame.

Recognized Plot frames: plot_start1.png, battleTutorial1.png, battleTutorial2.png, catchTutorial.png, fieldMovement.png, dungeonMovement.png, monsterChange1.png, monsterChange2.png, soulStoneTutorial1.png through soulStoneTutorial3.png, insertSoulStoneTutorial1.png, insertSoulStoneTutorial2.png, spiritTutorial.png, combineTutorial1.png, combineTutorial2.png. Recognition makes the bytes addressable; it does not by itself enable the intro.

Bitmap fonts

A text BMFont descriptor needs one well-formed info line with exactly one quoted face attribute and a page file the importer can resolve (<page>-hd.png preferred). The authored face may be anything; the loader re-keys each font by manifest identity so descriptors cannot collide. The four required identities are roles, not a requirement to ship any particular font program.

Audio

Manifest keys are extensionless stems. Any required stem accepts .m4a, .mp3, or .wav; the blob URL carries the real MIME type (audio/mp4, audio/mpeg, audio/wav). On a same-stem collision the projection visits M4A, then MP3, then WAV, and the later format wins.

Particles

A particle plist enters the manifest when its textureFileName resolves. The native point-list renderer requires a positive safe-integer maxParticles and has no quad or index-buffer ceiling. Required: PoisonParticles.plist, progressBarParticles.plist, destroyMonsterParticles.plist; Heal.plist when a reachable kit heals; Sparkle.plist when dungeon-capable.

Saves and Online

Save compatibility identity

Browser-local saves are keyed by a SHA-256 over a canonical, path-sorted projection of the identity-bearing plists (scope dib-identity-plists-v7): Monsters, Jobs, Abilities, AbilityComponents, Combines, plus any present Buffs, Items, Licenses, Tournaments, Towns, Worlds, PointsOfInterest, World_*, Quests, and root Collection. Dictionary keys are sorted before hashing. Archive name, ZIP metadata, compression, images, audio, and other presentation bytes do not participate, so an equivalent repack keeps its saves; changing a species, recipe, world graph, or collection goal intentionally selects a new save namespace.

Older v1–v6 slots and backups migrate lazily on the first successful v7 write, but only when they carry no Collection claims. Claimed historical state is shown as occupied and incompatible and is never decoded or cleaned up. Never copy claims across fingerprints or delete an incompatible slot to make a package look compatible.

Online logic identity

Online play uses a separate logic-v1:<sha256> identity computed over the reviewed mechanics-bearing plist families and excluding media, localization, AirshipConfig.plist, and presentation-only keys. The browser sends only that id and semantic commands; it never uploads the archive, a plist, or a compiled pack. The operator independently compiles and installs the matching trusted mechanics; unknown ids fail closed. Presentation-only edits must keep the logic id; any mechanics-bearing edit must change it. Compare your archive's browser id with the operator result from compileExtractedLogicPackIdentityV1 in @dib/logic-pack/node.

Validate

A successful ZIP parse is the first gate, not the last. A release candidate passes the envelope, schema, reference-closure, runtime, presentation, and reproducibility checks.

Commands

From the engine repository root:

pnpm test
pnpm typecheck
pnpm content:boundary

Then run the opt-in real-archive test against your package. It proves schema, component, and asset closure, builds a 6v6 roster from the first twelve monsters, runs authored moves to a terminal deterministic battle, and builds a muted scene: 

$env:DIB_TEST_CONTENT_ARCHIVE = 'path\to\YourPackage.ipa'
pnpm --filter @dib/web exec vitest run tests/runtimeContentArchive.test.ts
Remove-Item Env:\DIB_TEST_CONTENT_ARCHIVE

content:boundary builds the client and fails if the distribution contains game-content file types or binary signatures. It is a packaging control, not a legal opinion.

Browser scenarios

With the dev server running, point DIB_CONTENT_ARCHIVE at your package and run the muted Chromium scenarios that match the capabilities you promote. Scenario assertions and fixture requirements vary: inspect each scenario before selecting it for a custom package. The local-content scenario checks the import and battle flow, outbound writes, viewport overflow, and errors; evidence lands under output/. 

$env:DIB_CONTENT_ARCHIVE = 'path\to\YourPackage.ipa'
pnpm scenario:local-content      # import, attestation, six-monster battle
pnpm scenario:town               # arrival, notifications, Monsters style 0, departure
pnpm scenario:world-menu         # Master Menu, Town Portal direct return
pnpm scenario:guild-quest-ui     # Tavern actions, quest rows, Chat descriptions
pnpm scenario:fixed-encounter    # quest-gated fixed battle, breeder capture prevention
pnpm scenario:monsterpedia       # DIB_MONSTERPEDIA_DISPLAY_MODE = iphone | ipad
pnpm scenario:egg-hatch          # DIB_EGG_DISPLAY_MODE = iphone | ipad
Remove-Item Env:\DIB_CONTENT_ARCHIVE

Monsterpedia and Egg scenarios take a display mode and an output directory (DIB_MONSTERPEDIA_OUTPUT, DIB_EGG_OUTPUT) so runs do not overwrite each other. For the Clone Egg branch set DIB_EGG_KIND=silver and DIB_EGG_REPEAT_PICKS=<count>. Inspect the screenshots; state and error assertions alone are not a presentation check.

Release checklist

  • Two clean builds produce identical archive and source-kit SHA-256 hashes.
  • Every asset and dependency has recorded provenance and license text; ASSET_PROVENANCE.csv or THIRD_PARTY_ASSETS.txt is surfaced by the loader but never trusted as proof.
  • The archive contains no private keys, credentials, build-machine paths, executables, or unnecessary vendor metadata.
  • Capability claims distinguish runtime-validated systems from retained structure-only families.
  • Validation reports and build manifests match the exact published artifacts.
  • The compiled archive stays separate from the engine distribution and enters only through explicit user selection.
  • Ownership review is done. Compatibility and collision checks do not establish copyright, trademark, or license rights.

Asset archive limits

These limits describe the base resource importer. Offline code mods execute with full client access.

  • Load from a URL, an upload endpoint, a CDN, or an embedded default. Archives enter only through the file chooser; the last-used copy is a client-only cache that is discarded before a save write when storage is scarce.
  • Execute JavaScript or use an external URL as an imported resource. The resource catalog resolves retained local bytes. Offline code mods can separately make network requests; the game page's CSP is not a mod sandbox.
  • Select a loader, relax a check, or claim a capability through DIBContentManifest.plist or any other metadata.
  • Register or upload trusted mechanics for Online play. The operator compiles and installs the logic pack; players send only its id.
  • Supply Black Market cards, images, or destinations. The two demo records are app-owned and the screen is disabled by default.
  • Add executables, signatures, provisioning profiles, or a native remote service. They are discarded on import.
  • Prove ownership. Provenance files are surfaced for review, not trusted, and the user must attest to their rights on every new byte stream.
